## 根因与复现

`TradingService.consume` 原以最近完整日线日期 `completed_date()` 作为 `_live_after`，只比较 bar 的日期。这个日期代表可接受数据范围，无法代表实际会话/信号的生效时刻。

1. **R1 已确认**：2026-11-09 10:00 北京时间首次观察 11-06 收盘，completed_date 为 11-08；盘后补入 11-09 日线时，旧实现错误补记 11-09 09:30 买入。09:30 恰好启动及17:00观察也错误成交；盘前09:29:59观察应允许当日开盘。
2. **R2 已复现**：11-06观察后暂停或重启，11-09恢复且10:00才重新观察有效数据，即使该次同步没有新行，旧实现仍补记当天09:30买入。已有900股持仓的会话在11-11 10:00恢复、盘后补齐暂停期间行情，旧实现还会补记恢复前的11-11开盘卖出；修复后资金和已有成交保留。
3. **同源批量路径已确认**：11-06已观察买入信号，会话持续运行；11-10晚间一次取得11-09/11-10两根日线，旧实现把此时才生成的11-09卖出信号用于11-10开盘。修复后只允许原已生效信号对应的11-09买入，新卖出信号等待11-11开盘。
4. **重复 start**：旧实现即使 running 仍更新状态说明/时间；加入激活时钟后如果沿用此分支还会重置边界。因此 running 直接返回当前会话，既保持冻结组合，也不重置时钟。

## 最小变更

- `app/trading/service.py` 增加可注入的独立墙钟，默认 aware UTC datetime。实际 paused→running 保存 `_activated_at`，并要求重新观察有效数据；时间字段与既有账本一起事务化持久化。
- 有效行情取得并通过现有检查后，记录首次观察时刻；每次产生新 pending 信号后更新 `_signal_observed_at`。无行情/过期行情不会提前建立有效观察时钟；同数据重复同步不会反复重置已生效信号。
- 对增量成交，将 bar 日期转换为北京时间09:30，要求其严格晚于激活时刻和对应信号观察时刻。早于这些时刻的日线继续预热指标与信号，不执行订单。`completed_date` 仅用于日线完整性和既有 freshness 判断，不再用作授权成交时钟。
- 盘前已取得数据可参与同日开盘；盘中/盘后首次观察或恢复不能回填当天开盘。服务重启仍由原逻辑保守 paused，显式恢复时应用新边界。旧会话缺时间字段时保守以实际观察时刻建立边界。
- 回测、历史回放及纯确定性 engine 无改动；沿用已有冻结版本、订单/请求幂等、数据修订拒绝、现金/费用/T+1逻辑。暂停后的显式恢复仍校验源组合，running 的重复 start 返回现状。
- `frontend/trading.js` 的增量模式说明及 `docs/phase-2-api.md` 同步以上行为。状态说明不再错误暗示盘前观察也必须等待下一个交易日。
