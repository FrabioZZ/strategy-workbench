## R1：盘中首次启动可补记启动前的开盘成交（必须修复）

位置：app/trading/service.py consume，bootstrap 的 `_live_after=completed_date().isoformat()`，后续 trade 只比较 bar.date > _live_after。

根因：completed_date 是“可接受的最近完整日线日期”，不是会话首次实际观察/启动时间。北京时间 2026-11-09 周一10:00时该函数返回11-08，系统之后允许11-09开盘成交；9:30已在启动之前。不能用最近已完结日线日期替代执行授权时钟。

隔离复现（未使用HTTP、未修改SQLite）：构造纯 TradingService / new_ledger，阈值买入<=10，初始10000元；首批11-06收盘9.5，模拟11-09 10:00首次观察，此时 service.completed_date 返回11-08。首批consume仅预热，_live_after=11-08。收盘后返回11-09，补入11-09开盘10、收盘10.4的合法日线，再consume。实际产生11-09按10元买900股、费用5元的fill，早于首次观察。

实际工具输出：

```
bootstrap_at=2026-11-09 10:00 +08:00 live_after= 2026-11-08 fills= 0
after Monday close fills= [{'signal_date': '2026-11-06', 'date': '2026-11-09', 'symbol': '600000.SH', 'side': 'buy', 'quantity': 900, 'price': 10.0, 'fee': 5.0, 'order_id': '2026-11-06:2026-11-09:buy'}]
```

验收预期：待执行日线的开盘时刻必须晚于对应会话的实际启动/首次产生有效信号的观察时刻；盘中首次开启不能回填当天早上的成交。已结束的旧日线仍可用于指标预热，不可作为当前委托。可采用保守的“启动当日日线只预热”边界，但必须在界面/API文档中明确并保持测试时钟独立可控；若按9:30精确比较则同时覆盖盘前启动可执行当日开盘、盘后启动等待下一交易日。

## R2：暂停后恢复需检查同类时间边界

这是待修复线程验证的关联路径，尚未宣称已复现：start 当前不更新任何观察边界，长期暂停后resume可能消费暂停期间补入的行情并补成交。请先用行为测试确认；如果确实会补记暂停期成交，采用与R1一致的实际激活时间门槛。重复start在已running时必须幂等，不反复重置有效边界；暂停不丢账本，重启恢复应用新激活边界。
